# Firepower MPF Project — Codex Instructions

## Project Purpose

This repository is a modern Mission Pinball Framework (MPF) implementation of the 1980 Williams **Firepower** pinball machine.

The objective is to reproduce the original Firepower rules and behavior as faithfully as practical while running on modern hardware. Changes should preserve already-working behavior and should not introduce new interpretations of the game rules without explicit discussion.

This is an actively tested physical pinball machine, not merely a simulation.

---

## Hardware

* Original game: Williams Firepower (1980)
* Host computer: Raspberry Pi 4
* Pinball controller: FAST Pinball Neuron
* MPF communicates directly between the Raspberry Pi and FAST Neuron.
* Physical balls installed: **3**
* `s_coin_left` and `s_coin_right` are the two physical normally-open paid coin-drop switches.
* `s_service_coin` is currently referenced by `credits.service_credits_switch` but is not defined. A service-credit switch is conceptually a separate operator/service input; do not assume that either paid coin switch is its intended replacement.
* Physical ball locks:

  * `bd_lock1`
  * `bd_lock2`
  * `bd_lock3`
* Trough:

  * Mission Pinball multiple-switch / two-coil trough
  * Three physical trough switches
* Drain device:

  * `bd_drain`
  * `entrance_count_delay: 500ms` has previously been used to improve ball accounting.

Known historically troublesome switches:

* `s_lock_1` has been unreliable and has previously failed to detect a legitimately locked ball or produced questionable transitions.
* `s_lock_3` has occasionally been unreliable.
* Star rollover switches sometimes remain closed. Because these are physical rollover switches, a stuck state there is not automatically evidence of a software fault.

Do not compensate in software for a suspected hardware fault without first identifying that this is what the proposed change is doing.

# Canonical Firepower Game Rules

These rules are important. Do not merge systems merely because their names or lamps appear related.

## Multiball Qualification

Firepower multiball is qualified by the **six center arrow targets**.

At the beginning of qualification:

* The six targets blink.
* Hitting a target changes its lamp from blinking to steady.
* Partial target progress is intended to carry across balls for the same player. The original Firepower factory setting uses target memory.
* The current `shield_qualifier` configuration resets these shot states on `ball_ended`. That reset is a known implementation defect, not intended behavior.

Completing all six targets qualifies locks.

Completed lock qualification persists per player across balls. This is separate from the six individual target-memory states.

The established qualification sequence is:

1. First completion qualifies Lock 1 and Lock 2.
2. Further qualification enables Lock 3 as required by the Firepower rules/configuration.
3. Once the required three balls are locked, Firepower multiball starts.

Multiball uses three physical lock ball devices:

* `bd_lock1`
* `bd_lock2`
* `bd_lock3`

Do not treat the current multiball device settings as canonical Firepower rules. The current lock and multiball configuration contains known implementation defects documented below and must be traced against the installed MPF version before changes are proposed.

The current explicit startup request event is:

`start_firepower_multiball`

It is posted conditionally from the three separate per-lock full events:

* `multiball_lock_firepower_lock_1_full`
* `multiball_lock_firepower_lock_2_full`
* `multiball_lock_firepower_lock_3_full`

`multiball_lock_firepower_full` is a historical name and is not the event generated by the current three-lock configuration. Verify actual definitions before changing any of these names.

### Multiball release presentation

The intended speech sequence is:

1. "Fire"
2. "One"
3. "Two"
4. "Three"

The current release show does not implement this sequence and is not currently connected to multiball startup. See Known Current Implementation Defects.

# FIRE Lanes and Playfield Bonus Multiplier

The four top rollover lanes spelling:

F I R E

are **not multiball qualification**.

They control the end-of-ball playfield bonus multiplier.

Each rollover scores **1,000 points whether lit or unlit**.

Completing FIRE advances the multiplier through:

* 2X
* 3X
* 4X
* 5X

Associated lamps include:

* `l_bonus_multiplier_2x`
* `l_bonus_multiplier_3x`
* `l_bonus_multiplier_4x`
* `l_bonus_multiplier_5x`

FIRE-lane progress has been designed to carry across balls as appropriate to the original game rules.

Lane-change functionality applies to these FIRE lanes.

A FIRE-lane completion chase show has previously been implemented.

Do not connect FIRE-lane completion to multiball qualification.

# FIRE / POWER Bonus

The large FIRE and POWER feature is a **separate system from multiball**.

This distinction is critical.

Completing FIRE and POWER awards the Firepower bonus progression:

1. 10,000
2. 30,000
3. 50,000
4. Special

After completing a complete progression, subsequent qualification begins again at 10,000 rather than immediately awarding another Special.

Memory for the FIREPOWER 10K/30K/50K award lamps was operator-adjustable on the original machine. Do not describe reset-at-ball-end behavior as an immutable original rule.

If this project intentionally resets FIRE/POWER qualification or award-lamp state at ball end, document that as project-specific behavior and keep it distinct from the original machine's operator-adjustable rule.

The large FIRE and POWER lamps should extinguish after the corresponding award sequence rather than remaining incorrectly illuminated.

An alternating FIRE/POWER lamp celebration has previously been implemented and tuned to approximately:

* 70 ms steps
* 3 loops

The exact existing show definitions should be inspected before modification.

### Special

When Special is lit through the FIRE/POWER progression, it is consumed by the appropriate outlane switch:

* `s_left_out_lane`
* `s_right_out_lane`

Do not confuse this feature with lock qualification or multiball.

# End-of-Ball Bonus

The Firepower end-of-ball bonus system is custom and should not be replaced with assumptions copied from another Williams game.

Relevant player variables have included:

* `bonus_value`
* `bonus_multiplier`

Intended limits:

* `bonus_value`: 0–29
* `bonus_multiplier`: 1–5

Bonus lamps represent the current bonus value in decades and units:

* 1 through 10
* 20

The 10K and 20K lamps are decade indicators. They must not be treated as additive indicators that permit values 30–39.

Maximum collectible base bonus is 29 units, or 29,000 points before multiplier. The current `bonus_ladder` implementation incorrectly permits values through 39; this is a known implementation defect.

At end of ball, the bonus should count down visibly and audibly.

The total number of countdown passes equals the displayed FIRE-lane multiplier. Therefore a 5X multiplier collects the base bonus five times total, not six.

During countdown:

* score should increment correctly;
* bonus lamps should decrement in synchronization;
* the bonus sound should play for each step.

Bonus value and bonus multiplier reset appropriately at the end of the ball.

This subsystem has had unresolved implementation problems and must be inspected carefully before assuming the current configuration works.

# Ball Accounting and Ball Search

Ball accounting has been one of the most sensitive areas of this project.

Do not make casual changes to:

* ball device counts;
* eject events;
* lock devices;
* trough configuration;
* ball-search behavior;
* unexpected-ball handling;
* switch activation/deactivation behavior.

A legitimately locked ball should remain recognized as belonging to its lock device.

There have previously been cases where ball search appeared to pulse a lock eject coil even though the device should have been holding a legitimately locked ball.

There have also been cases where MPF reported that the playfield still contained balls even though all three physical balls were visibly in the trough.

`s_lock_1` false or missed transitions have been suspected as a possible contributor.

When diagnosing ball-accounting problems:

1. Trace actual MPF events and device state.
2. Compare switch transitions against physical ball locations.
3. Determine which ball device MPF believes owns each ball.
4. Do not immediately add compensating eject events or count corrections.
5. Check whether a hardware switch problem can explain the discrepancy.

Ball search must not intentionally eject legitimately retained lock balls simply to resolve bookkeeping unless that behavior is explicitly required by MPF and understood.

# Known Current Implementation Defects

These are observed discrepancies in the current working configuration, not intended Firepower behavior. Re-check the repository and installed MPF version before fixing them, since this section may lag behind later implementation work.

## Center-arrow target memory

The six `arrow_target_1` through `arrow_target_6` shot states are player-specific, but all three groups in `shield_qualifier` currently include `ball_ended` in `restart_events`. This resets partial 1–6 target progress between balls. Intended behavior is to preserve that partial progress for the same player.

Completed lock qualification is tracked separately by per-player lock variables and currently persists between balls.

## Physical locks and multiball startup

The current multiball and lock settings are not canonical and have several related defects:

* The `firepower` multiball does not list `bd_lock1`, `bd_lock2`, and `bd_lock3` under `ball_locks`, so the multiball device is not configured to release its balls from the three physical locks.
* Each one-ball multiball lock currently uses `balls_to_replace: 1`. This requests a replacement for the third physical lock as well as the first two even though the machine has only three installed balls, creating a potentially unsatisfiable or stale add-ball request.
* `start_firepower_multiball` is both the mode start event and the multiball device start event. Because the multiball device is newly loaded when that event starts the mode, it may not receive the first occurrence of the same event.
* `firepower_multiball_release.yaml` and `start_firepower_multiball_delay.yaml` are not invoked by the active configuration.
* The `eject_firepower_lock_1`, `eject_firepower_lock_2`, and `eject_firepower_lock_3` events in the release show have no active handlers.
* The orphaned release show repeats "Fire" before every number. The intended speech sequence is "Fire", "One", "Two", "Three".

These defects can leave physical lock balls retained while MPF requests balls from the normal playfield source, and can contribute to incorrect or stalled ball accounting.

## End-of-ball bonus range

The current `bonus_ladder` increments `bonus_value` while it is below 39 and lights the 10K and 20K lamps together for values 30–39. Intended range is 0–29, with a maximum base collection of 29,000 points before multiplier. The current 30–39 behavior is a defect.

## Service-credit switch

`credits.yaml` references `s_service_coin`, but no such switch is defined. `s_coin_left` and `s_coin_right` are the two paid coin-drop switches and must not be silently substituted for the missing operator/service-credit input.

# Current Areas Requiring Attention

The following issues were still under investigation during the most recent major debugging sessions. Inspect the current repository and recent logs before assuming each is still present.

## Lock lamp memory

Lock lamps have sometimes failed to preserve the correct visual state across balls even though physical balls remained locked.

## FIRE lamp memory

POWER state has previously survived a ball transition while the corresponding FIRE lamp state did not.

## `s_lock_1`

The physical switch has been cleaned, but false or missed transitions remain historically important when diagnosing phantom playfield counts or lost-ball recovery.

## End-of-ball bonus countdown

A previous implementation failed to visibly count bonus, play the expected sound, or score the countdown. Expected bonus-mode events were sometimes absent from the MPF log.

## Lane-change startup

There has been an intermittent condition where the first rollover activation of a new ball did not appear to participate in lane-change behavior.

## Lost-ball recovery

There have been incidents involving:

* "playfield still contains balls" when all balls appeared physically accounted for;
* unexpected ball-search activity;
* lock eject coils being pulsed during later ball-search passes.

Treat these as diagnostic history, not automatically as proof that the current configuration still contains the same defect.

# Working Rules for Codex

## Before editing

For non-trivial changes:

1. Inspect all relevant configuration and mode files.
2. Trace definitions and references across the repository.
3. Determine the current behavior from the actual files rather than relying exclusively on this document.
4. Identify any conflict between this document and the repository.
5. If the requested task is diagnostic, report the likely cause before changing files unless explicitly asked to make the change immediately.

## Cross-reference validation

Whenever modifying MPF configuration, check affected references for:

* switch names;
* coil names;
* light names;
* ball-device names;
* mode names;
* event names;
* show names;
* player-variable names;
* machine-variable names;
* timers;
* counters;
* achievements or logic blocks;
* event-player targets;
* mode start and stop events.

Search the whole repository when necessary.

A configuration entry that references a plausible-looking but nonexistent MPF object is a defect.

## YAML editing

Preserve:

* `#config_version=6`
* valid YAML indentation;
* existing comments that remain accurate;
* established naming conventions;
* unrelated working configuration.

Do not perform broad formatting or cleanup while fixing an unrelated functional problem.

Do not silently rename events or devices.

## Scope control

Prefer the smallest coherent change that fixes the identified problem.

Before changing a working subsystem to solve a problem elsewhere, establish the dependency that requires that change.

Avoid rewriting entire modes unless the existing design itself is the source of the problem.

## Analysis versus modification

When asked to "review," "analyze," "trace," "find," or "determine," do not modify files unless modification is also explicitly requested.

When asked to make a change, explain:

* the root cause;
* which files were changed;
* why each change is necessary;
* what behavior should be tested on the physical machine.

## Physical-machine caution

This project controls real coils, lamps, switches, and balls.

Do not create rapid or indefinite coil-firing loops.

Do not substantially increase coil pulse duration or power without explicit justification.

Be especially cautious with:

* ball eject coils;
* trough coils;
* lock eject coils;
* ball-search actions.

## Testing

When possible, distinguish among:

* configuration syntax validation;
* MPF event/logical testing;
* physical-machine testing.

Passing configuration validation does not prove correct physical ball behavior.

When diagnosing a physical-machine failure, specify what MPF log events or switch transitions would confirm or falsify the diagnosis.
